## 1. Pfleger-Verwaltung

### User Story 1: Pflegekräfte anzeigen

**User Story**

> Als Wohnbereichsleiter möchte ich alle Pflegekräfte in einer Übersicht sehen können, um schnell geeignete Mitarbeiter für die Dienstplanung zu finden.

Akzeptanzkriterien

A_1 Eine Tabelle mit Spalten ID, Vorname, Nachname und Telefonnummer zeigt alle Pflegekräfte aus der Datenbank.
A_2 Die Tabelle wird beim Start der Anwendung automatisch gefüllt und nach jeder Änderung aktualisiert.

Tasks

T_1 pfleger-Tabelle in Datenbank mit Feldern (id, firstname, surname, telephone) erstellen.
T_2 Caregiver-Modellklasse mit Properties (id, firstName, surname, telephone) erstellen.
T_3 CaregiverDao mit Methode readAll() implementieren.
T_4 AllCaregiverController mit initialize() und readAllAndShowInTableView() implementieren.
T_5 TableView mit Spalten-Mappings konfigurieren.

Testfälle

TF1: Pflegekräfte anzeigen

### User Story 2: Pflegekraft anlegen

**User Story**

> Als Wohnbereichsleiter möchte ich neue Pflegekräfte anlegen können, um neue Mitarbeiter in die Dienstplanung aufnehmen zu können.

Akzeptanzkriterien

A_3 Über einen "Hinzufügen"-Button öffnet sich ein Dialog mit Eingabefeldern für Vorname, Nachname und Telefonnummer.
A_4 Nach dem Speichern wird die neue Pflegekraft mit eindeutiger ID in der Tabelle angezeigt und in der Datenbank gespeichert.
A_5 Wenn erforderliche Felder leer sind, wird eine Fehlermeldung angezeigt und die Pflegekraft wird nicht gespeichert.

Tasks

T_3 CaregiverDao Methode create() implementieren.
T_6 Eingabe-Validierung für erforderliche Felder implementieren.
Teil von T_4: handleAdd() implementieren.

Testfälle

TF1: Pflegekraft erfolgreich anlegen.
TF2: Validierung – leere Pflichtfelder beim Anlegen.

### User Story 3: Pflegekraft bearbeiten

**User Story**

> Als Wohnbereichsleiter möchte ich die Daten einer Pflegekraft ändern können, um aktuelle Mitarbeiterinformationen bereitzuhalten.

Akzeptanzkriterien

A_6 Ein Doppelklick auf eine Tabellenzeile ermöglicht das Bearbeiten der Felder.
A_7 Änderungen werden nach dem Speichern in der Datenbank persistiert und sofort in der Tabelle angezeigt.

Tasks

T_3 CaregiverDao Methode update() implementieren.
T_5 Edit-Commit-Listener konfigurieren.

Testfälle

TF3: Pflegekraft erfolgreich ändern

### User Story 4: Pflegekraft löschen

**User Story**

> Als Wohnbereichsleiter möchte ich ausgeschiedene Pflegekräfte aus dem System entfernen können, um die Personalliste aktuell zu halten.

Akzeptanzkriterien

A_8 Eine ausgewählte Pflegekraft kann über einen "Löschen"-Button nach Bestätigung entfernt werden.
A_9 Nach der Löschung verschwindet die Pflegekraft aus der Tabelle und der Datenbank.

Tasks

T_3 CaregiverDao Methode deleteById() implementieren.
Teil von T_4: handleDelete() implementieren.
T_7 Bestätigungsdialog beim Löschen implementieren.
T_8 ObservableList nach Löschvorgängen aktualisieren.

Testfälle

TF4: Pflegekraft löschen mit Bestätigung.
TF5: Löschen abbrechen.

### 5: Login System implementieren

**User Story**

> Als Administrator möchte ich, dass die Nutzer sich mit ihrem Benutzernamen und Passwort einloggen können, um auf die notwendigen Informationen zuzugreifen.

**Akzeptanzkriterien**

| Nr. | Kriterium |
|-----|-----------|
| A_1 | Ein Login-Fenster mit Benutzername- und Passwortfeld wird beim Start angezeigt |
| A_2 | Nach erfolgreichem Login wird die Hauptanwendung angezeigt |
| A_3 | Bei falschen Anmeldedaten wird eine Fehlermeldung angezeigt |
| A_4 | Das Passwortfeld wird bei fehlerhafter Eingabe geleert |
| A_5 | Jeder Benutzername im System ist eindeutig |

**Tasks**

| Nr. | Task                                                                            |

| T_2 | LoginController mit Authentifizierungs-Logik implementieren                     |

| T_4 | UserDao mit Methoden zur Suche nach Benutzername und Passwort-Prüfung erstellen |
| T_5 | users-Tabelle in der Datenbank anlegen                                          |
| T_6 | Main-Klasse ändern, um zuerst LoginController statt MainController zu starten   |

### User Story 6: Log-System (Audit-Logging) implementieren

**User Story**

> Als Datenschutzbeauftragter möchte ich, dass alle Zugriffe auf Patientendaten protokolliert werden (Wer hat wann was zugegriffen?), um die Compliance zu gewährleisten und Verstöße nachverfolgen zu können.

**Akzeptanzkriterien**

| Nr. | Kriterium |
|-----|-----------|
| A_1 | Jeder Zugriff auf Patientendaten wird mit Benutzer, Uhrzeit und Aktion geloggt |
| A_2 | Jede Änderung an Patientendaten wird geloggt (alte Wert, neue Wert, Feld) |
| A_3 | Löschung von Patienten wird geloggt |
| A_4 | Ein Administrator kann alle Logs einsehen und filtern (nach Datum, Benutzer, Patient) |
| A_5 | Logs können nicht gelöscht werden (nur Lesen) |

**Tasks**

| Nr. | Task |
|-----|------|
| T_1 | AuditLog-Modellklasse mit Properties (id, userId, action, patientId, timestamp, details) erstellen |
| T_2 | audit_logs-Tabelle in Datenbank erstellen (id, user_id, action, patient_id, timestamp, details) |
| T_3 | AuditLogDao mit create() und readAll() Methoden implementieren |
| T_4 | AuditLogService erstellen mit logAction()-Methode |
| T_5 | PatientDao.readAll(), read() Aufrufe mit AuditLogService.logAction("READ") erweitern |
| T_6 | PatientDao.update() mit Logging der Änderungen erweitern |
| T_7 | PatientDao.deleteById() mit Logging erweitern |
| T_8 | AllAuditLogController und AllAuditLogView.fxml für Anzeige und Filterung erstellen |

**Testfälle**

**TF1: Patient-Zugriff wird geloggt**

|---|---|
| **Vorbedingung** | Benutzer "pfleger1" ist angemeldet, Log-System ist aktiv |

**TF2: Patient-Änderung wird geloggt**

| **Testschritte** | 1. Patient "Anna Schmidt" öffnen; 2. Telefonnummer von "123-456" zu "999-888" ändern; 3. Speichern |
| **Erwartetes Ergebnis** | Log-Eintrag zeigt: Action="UPDATE", Field="telephone", OldValue="123-456", NewValue="999-888" |

## 3. Qualitätscheck

### INVEST-Kriterien

| Story | I | N | V | E | S | T | Anmerkung |
|---|---|---|---|---|---|---|---|
| US 1 - Pflegekräfte anzeigen | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | Kleine, klar abgegrenzte Story |
| US 2 - Pflegekraft anlegen | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | Neue Mitarbeiter können erfasst werden |
| US 3 - Pflegekraft bearbeiten | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | Änderungen an Mitarbeiterdaten möglich |
| US 4 - Pflegekraft löschen | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | Ausgeschiedene Mitarbeiter können entfernt werden |
| US 5 - Login System | ✓ | ✓ | ✓ | ~ | ~ | ✓ | Mittel (2–3 Tage); View-Integration erforderlich |
| US 6 - Log-System | ~ | ✓ | ✓ | ~ | ~ | ✓ | Abhängig von US 5 (Login) |
| US 7 - Patienten archivieren | ✓ | ✓ | ✓ | ✓ | ~ | ✓ | Mehrere Views und Datenbankänderungen |
| US 8 - Pflegekraft einer Behandlung zuweisen | ✓ | ✓ | ✓ | ~ | ~ | ✓ | Betrifft mehrere Module |

**Anmerkungen:**
- **I (Independent):** US6 hängt von US5 ab, die übrigen Stories sind weitgehend unabhängig.
- **N (Negotiable):** Die konkrete Umsetzung kann diskutiert werden.
- **V (Valuable):** Alle Stories liefern einen erkennbaren Nutzen für Pflegepersonal oder Datenschutz.
- **E (Estimable):** Der Aufwand ist für alle Stories grob abschätzbar.
- **S (Small):** US1–US4 wurden aus dem ursprünglichen CRUD-Epic aufgeteilt und sind nun klein genug.
- **T (Testable):** Für alle Stories können konkrete Testfälle definiert werden.
